# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project state

Dolly is a Go tool (Go 1.22+, built on `github.com/go-ldap/ldap`) that replicates users and groups one way from Active Directory to OpenLDAP. The repo holds the spec (`README.md`), the user docs (`docs/`, `zensical.toml`), `dolly.yaml.template`, the CI, release, and docs workflows, `.goreleaser.yaml`, and the Go code. Step 1 is done: config, model, `Source` interface with a fake, the pure planner, and dry-run printing (`--fixture` feeds it snapshots). Also done: the real AD source (`internal/source/ad.go`), step 2 (`internal/target`: reader, applier, run lock, `cn=status`), a live `dolly sync --dry-run`, real `dolly sync` and `dolly adopt`, and `dolly unlock`. Next is step 4 (install, check, SMTP; notification decisions go where `TODO(notify)` marks them in `internal/target/status.go` and `cmd/dolly/main.go`). `README.md` is the spec: CLI surface, config schema (`dolly.yaml`), and sync algorithm. Keep it in sync when behavior changes.

Layout and commands:

```bash
go build -o dolly ./cmd/dolly      # entry point; /dolly is git-ignored
go run ./cmd/dolly sync --dry-run --fixture cmd/dolly/testdata/fixture.yaml --config dolly.yaml.template
go test ./...
go test ./path/to/pkg -run TestName   # single test
```

CLI: `dolly sync [--users|--groups] [--dry-run] [--force] [--debug]`, `dolly adopt [--dry-run] [--debug]`, `dolly unlock [--yes]`, `dolly check`, `dolly install`, `dolly uninstall`, `dolly version`.

Releases: pushing a `v*` tag runs `.github/workflows/release.yml` (GoReleaser, config in `.goreleaser.yaml`, static `CGO_ENABLED=0` builds for linux/darwin × amd64/arm64). `cmd/dolly` must declare `var version, commit, date string`, which are set via `-ldflags -X main.…`. CI (`.github/workflows/ci.yml`) runs `gofmt -l`, `go vet`, `go test -race`, and `goreleaser check`, and triggers only on Go, module, or workflow changes. Local Go is the distro package (`/usr/bin/go`, 1.22.2). Keep `go.mod`'s `go` directive at 1.22 unless a dependency forces it higher. In that case `GOTOOLCHAIN=auto` fetches the newer toolchain, and the README's minimum version must be updated.

Exit codes: `0` success or lock held elsewhere, `1` error, `2` guard tripped. There is no `dolly diff` (use `sync --dry-run`).

## Architecture and testing

- **Packages:** `cmd/dolly` (CLI on stdlib `flag`, exit codes), `internal/config` (load, lookup order, validation, secrets read lazily when used), `internal/model` (entries, snapshots, ownership records, objectGUID, DN keys via `ldap.ParseDN`, ASCII table), `internal/source` (`Source` interface, `Fake`, `Read` which follows out-of-scope members), `internal/planner` (pure planner, ops, plan printer, rule tests in `rules_test.go`, dependency keys in `deps.go`), `internal/fixture` (the `--fixture` loader), `internal/target` (reader, `Apply`, run lock, `cn=status`, all behind the small `Conn` interface), `internal/ldapfake` (in-memory `Conn` with real result codes, for tests). `template.go` at the root embeds `dolly.yaml.template` (`go:embed` can't reach a parent directory).
- **Native LDAP only.** All reads and writes go through `go-ldap`. Never shell out to `ldapmodify`, `slapadd`, or similar, and never write LDIF files. The only external command is `systemctl --user` in `dolly install`.
- **The planner is a pure function:** (AD snapshot, target snapshot, ownership records, config) → ordered plan of operations. It does no I/O. All the ownership rules live there, covered by table-driven tests, one per rule in the README's "Ownership records" list. `--dry-run` prints the same plan that a real run applies.
- **AD access sits behind a `Source` interface** with an in-memory fake for tests, because no test AD exists yet (a test OU and test LDAP server are TBD).
- **The applier never reorders the plan.** Each op carries dependency keys (`Needs`, `Provides`; see `internal/planner/deps.go`): when an op fails, it and every later op needing a key it provides are skipped, transitively; everything else still runs (per-entry errors never abort). Keys: `entry:<DN>`, `seq:<record DN>` (one user's or group's crash-safe sequence), `pair:<group>|<user>` (one membership), `placeholder:<group>`, `adds:<group>`. A new planner rule must set them so a failure behaves like a crash at that point for everything that depends on it. Only `entryAlreadyExists` with matching content, `attributeOrValueExists` on a single-value add, and `noSuchAttribute` on a single-value delete count as already done. A value rename (`RenameMember`, or a record update that deletes one `roleOccupant` and adds one) rejected with `noSuchAttribute`/`attributeOrValueExists` is re-read (`renameValue` in `internal/target/apply.go`), because the `refint` overlay may already have rewritten it after the `modrdn`: old gone and new present is already done, both gone is left alone (never recreate what may be a local member; an owned one is re-added by the next run), both present deletes the old one.
- **Real-run flow** (`cmd/dolly` `realRun`): writer connection (not tied to the run context, so the lock can be released after `SIGTERM`), create `state_base` if missing, lock, read, plan, guard, apply, `cn=status`, release (fresh `network_timeout` context, only if still ours). `readSnapshots` and `dialWriter` are package variables so tests run it against `ldapfake` and a fixture.
- **Integration tests** for the target side run against a real OpenLDAP behind the `integration` build tag (`internal/target/integration_test.go`, env `DOLLY_IT_URL`, `DOLLY_IT_BIND_DN`, `DOLLY_IT_PASSWORD`, `DOLLY_IT_BASE`, optional `DOLLY_IT_SCHEMA=rfc2307`; skipped when unset unless `DOLLY_IT_REQUIRED` is set). The `integration` CI job runs them against an `osixia/openldap` service container with rfc2307bis. `ci.yml` triggers on Go, module, GoReleaser, and workflow (`ci.yml`, `release.yml`) changes.

## Hard requirements

1. **Never wipe and rebuild the target.** Every run reads *all* in-scope groups from AD, and all in-scope users in every run that syncs users (no `uSNChanged` incremental mode, because it misses deletions and nested-group changes; about 10,000 groups is cheap). A groups-only run reads neither the AD users base nor the target's `users_base` in full: it resolves members by base-scope DN lookups (a small worker pool, following nested groups) and asks the target only about the uids it needs (`(|(uid=a)…)` in chunks of 50, requesting only `uid`). The AD users base can be huge, and `users_base` can be read-only and larger than the server's hard size limit. Every DN lookup must match `source.users.filter` or `source.groups.filter`; a member that matches neither is skipped as filtered (a summary count, not an error). **Never plan from partial data:** if any AD or target read errors or is truncated (`sizeLimitExceeded`; the old server config has `olcSizeLimit: 10000` and only the rootdn bypasses it), abort the run. `source.urls` is a list of DCs tried in order. Then Dolly applies minimal add, modify, modrdn, and delete operations against the running server.
2. **Only touch what Dolly owns.** Target groups can hold members added directly on the LDAP server. On sync, add members newly in the AD group, and remove members that Dolly previously replicated but that are no longer in the AD group or no longer in AD. Leave every other member alone. Never compute membership as "replace with AD's list", and never replace a whole `member` or `memberUid` attribute. Add and delete individual values. Only write the attributes listed in the mapping. The details are in the README sections "Ownership records" and "Adopting an existing tree":
   - **Ownership lives in the target LDAP**, not in a local file: `organizationalRole` entries under `state_base` (core schema only), named `cn=<objectGUID>`. `seeAlso` points to the managed entry, and `roleOccupant` lists the members Dolly added to a group. `memberUid` ownership is derived from those DNs. Records carry small `description` key=value notes: `missing-since` (RFC 3339 UTC), `saved-shell`, and `renaming-from=<old DN>` while a rename is in flight. A stale `renaming-from` must never touch a local entry that has since appeared at the old DN (when the managed entry is present at `seeAlso`). `cn=status` holds the last success, current failure, and last notification. Dolly creates `state_base` and its children if missing, but never `users_base` or `groups_base`.
   - **Crash-safe write order.** Write the ownership record *before* adding an entry or member, and remove the entry or member *before* removing its record. The reverse order would make a Dolly-added member look local after a crash, and it would never be removed.
   - **Identity is `objectGUID`.** AD returns it as 16 mixed-endian bytes. Format it one consistent way (canonical hyphenated string). Renames in AD become `modrdn`, followed by updating `member` and `memberUid` values in every group and the `seeAlso` and `roleOccupant` values in the records. A rename that collides with an existing entry is a conflict: log it and skip.
   - **Local wins.** A member already present without a record is local and is never removed, even if the same user is also in AD. A member value removed by hand is re-added only if Dolly owns it (a `roleOccupant` names it) and AD still lists it (AD wins for owned members); a local member removed by hand is never restored. Known consequence, kept without extra state: a local member who is also in the AD group comes back as a Dolly-owned member once removed by hand. A target entry that matches an AD entry by name but has no record is a conflict: log an error and skip it. `dolly adopt`, run once, is the only thing that claims existing entries.
   - **Groups are never deleted.** A group deleted from AD loses its owned members and its record. A user gone from AD (deleted, out of scope, or missing a required attribute) loses owned memberships immediately. The entry is deleted only with `prune_users` and after `prune_after_days` (tracked as `missing-since` in the record). Pruning also removes the user's *local* memberships, the one exception to "local wins", to avoid dangling members.
   - **Per-entry errors don't abort the run** (the old tool used `ldapmodify -c`). Log, continue, report in the summary, and exit 1. Aborts are for incomplete reads, the guard, and the lock.
   - **ID numbers.** Duplicate `uidNumber`/`gidNumber` values are summary warnings and never block. A changed `uidNumber`/`gidNumber` is applied and always reported.
   - **`uid` case is preserved** as in AD. LDAP matching is case-insensitive, so compare names case-insensitively, and treat a case-only change as a rename (`modrdn`).
   - **ASCII-only attributes** (`gecos`, IA5String syntax) must be transliterated to ASCII, or OpenLDAP rejects the entry. The old tool escaped them with `unicode_escape`.
   - **`create_only` attributes** (default `loginShell`, `homeDirectory`) are written at creation and never again, so local overrides survive.
   - **Two group schemas.** rfc2307bis (default: `groupOfNames` + auxiliary `posixGroup`, members as `member` and `memberUid`) and RFC 2307 (structural `posixGroup`, `memberUid` only; the first real target, an RFC 2307 server, is one). The membership list in the mapping decides. `roleOccupant` in ownership records is always a DN, `<rdn>=<uid>,<users_base>`, even with `memberUid` only, where it is just an identifier and the user entry needn't exist on the target. A groups-only run never writes target user entries.
   - **Empty groups** only matter with `member`: then they get the `empty_group_member` placeholder rather than violating `groupOfNames` (remove it once a real member exists), and new AD groups with no resolvable members aren't created yet. With `memberUid` only, groups may be empty and are created right away.
   - **Disabled accounts** (`userAccountControl & 0x2`) keep their entry, lose all *owned* memberships, and get `loginShell` set to `disabled_shell` (this overrides `create_only`, because SSH keys would still work). Save the previous shell in the record and restore it on re-enable. **`primaryGroupID` is ignored.**
   - **Required attributes.** A group member needs only the AD attribute its `uid` is mapped from (for example `sAMAccountName`). A user *entry* (created or managed by a users sync) needs every attribute in the users `required` list (the uid source, `uidNumber`, `gidNumber`; no 65534 default any more). A user missing one gets no entry and is listed once in the summary (only in runs that sync users), but stays a valid member. Groups need `name` and `gidNumber`; a group, or a user without a uid, is ignored everywhere, including for flattening, which differs from the old tool. Config validation requires the users `required` list to include the sources of `uid`, `uidNumber`, and `gidNumber` when they're plain attributes. The one exception is `dolly adopt`, which claims every AD user with a uid so the first sync can treat the incomplete ones as gone. List ignored entries in the run summary instead of warning on every run.
   - **ID range.** A `uidNumber` or `gidNumber` Dolly would write must be an integer in 0..4294967294 (`uid_t`/`gid_t` are unsigned 32-bit, and -1 is reserved). Anything else is ignored like a missing required attribute and listed once.
   - **Members must exist on the target** (always on, no config key; the removed `sync.require_member_on_target` is rejected with an explanation). A member is added only if an entry for it exists under `users_base` (Dolly-owned or local; by `uid` in memberUid-only mode, at the member DN in `member` mode; a user created earlier in the same run counts, one pruned in the same run doesn't). Otherwise it's skipped. In groups-only replication neither AD users nor target users need `uidNumber`: the target lookup requests only `uid` and filters only on `(uid=…)`, never on `objectClass` or `uidNumber`. Only groups need `gidNumber`. Skips are debug-level, not warnings, and never count toward a notification: the plan records the sorted (group, uid) pairs, the summary prints one count line (`members skipped: N not on the target (use --debug to list them)`, omitted when zero), and the `--debug` flag (accepted by `sync` and `adopt`) prints one `debug: skip <uid> in <group>: …` line per pair to stderr. A skipped member is re-evaluated every run and added once its entry exists. An owned member whose entry vanished is kept (neither re-added nor removed). The planner stays pure: the command layer gets the candidates from `planner.MemberCandidates`, looks them up, and passes the result in `TargetSnapshot.ExistingUsers`.
   - **Out-of-scope members** (outside the configured bases) that match the search filters and have a uid are followed. Users become members (and managed users, with every required attribute), and child groups are flattened but not created. Non-user, non-group members are skipped.
   - **Run lock in LDAP:** `cn=lock,<state_base>`, taken with an atomic LDAP add and holding the host, PID, and start time. Release it in a `defer` *and* on `SIGTERM`/`SIGINT` (a `defer` doesn't run on a signal, so use `signal.NotifyContext`). If the lock is held, exit 0 quietly with no mail. `--dry-run` takes no lock. Every run has a hard `run_timeout` shorter than `lock_ttl`, plus `network_timeout` on connects and operations. A lock is stale only when both the server's `createTimestamp` and the holder's `started=` note are at least `lock_ttl` old by the local clock (hosts must be NTP-synced). A `createTimestamp` more than 5 minutes in the local future is clock skew: refuse to judge the lock and exit 1 with an error naming the skew. A stale lock is broken by `modrdn` to `cn=lock-stale-<short host>-<unix>-<pid>` first (only one host can win the rename; `noSuchObject` or `entryAlreadyExists` there means the rename was lost), then deleted, with a warning and a notification. `dolly unlock` removes it by hand. There is no local lock file.
   - **Never open `dolly.yaml` or editor swap files like `.dolly.yaml.swp`** in the repo root. They hold real credentials. Tests use fixtures and the template. When a command must read a password from the config, mask every `password` field in any output.
   - **Mass-deletion guard.** Count removals across the whole run, separately for memberships and users. Abort with no writes (exit 2, send a notification) if a count exceeds both `max_delete_min` and `max_delete_percent` of what Dolly owns, or if AD returned zero users or zero groups. `--force` overrides.
3. **One Dolly per target.** Each target server has its own `state_base`, lock, and config. There is no multi-target mode. Several targets from one host means several config files and `--config`. The source `bind_dn` may be a DN or a UPN.
4. **Users and groups sync independently.** `--users` or `--groups` alone must work, and neither may assume the other ran in the same invocation.
5. **Users and groups only.** No computers, contacts, NIS netgroups, or autofs maps, even though the predecessor exported the last two.
6. **Unprivileged, XDG, systemd --user.** Dolly runs as a regular user by default and must never require root. `dolly install` self-installs the binary to `~/.local/bin`, creates `$XDG_CONFIG_HOME/dolly/dolly.yaml` from the template with mode `0600` (embed it with `go:embed`, and never overwrite an existing config), and writes `dolly.service` and `dolly.timer` to `$XDG_CONFIG_HOME/systemd/user/`. There is no local state or lock (both live in LDAP), and logs go to stdout/stderr for journald. Honor `XDG_CONFIG_HOME` and fall back to `~/.config`. Relative paths in the config resolve against the config file's directory. Secrets are written `0600`. No hardcoded `/etc` or `/var` paths. The README's "File locations (XDG)" table is the reference. Environment robustness (service accounts reached via `su -` or `sudo -iu` often lack a session environment):
   - **`XDG_RUNTIME_DIR` unset.** If `/run/user/<uid>` exists, set `XDG_RUNTIME_DIR` and `DBUS_SESSION_BUS_ADDRESS=unix:path=/run/user/<uid>/bus` in the environment of Dolly's own `systemctl --user` calls. If it doesn't exist, the user has no session and no linger: fail clearly and suggest `loginctl enable-linger <user>`.
   - **`~/.local/bin`.** Create it if missing, and warn (don't fail) if it isn't on `PATH`. Units reference `%h/.local/bin/dolly`, so they never depend on `PATH`. The timer has `RandomizedDelaySec=60` so two hosts don't fire in the same second.
   - **Directories.** Create the config directory on demand with `0700` (`os.MkdirAll`).
   - **Idempotent install.** Re-running `dolly install` is harmless: never overwrite an existing config, and rewrite units only when their content changed. `dolly uninstall` is the undo.
   - **Non-Linux.** Without systemd, install the binary and config, skip the units, and say so.
   - **Never edit the user's shell startup files** (`.bashrc`, `.profile`, and so on).
7. **Config and secrets.** Config lookup order is `--config`, then `./dolly.yaml`, then `$XDG_CONFIG_HOME/dolly/dolly.yaml`. A local `dolly.yaml` is git-ignored because it may contain passwords. Passwords can be inline (`bind_password`, `notify.password`) or in a file (`*_password_file`), never both non-empty (config error; an empty value counts as unset). With any inline password, refuse to run unless the config file is mode `0600` or stricter. The checked-in example is `dolly.yaml.template`. Keep the template, the README config block, and the config structs in sync, and never commit a real `dolly.yaml`.
8. **Email notifications.** The `notify` section configures SMTP (host, port, StartTLS, optional auth via `password` or `password_file`, from, to, subject prefix) and when to send: `failure`, `changes`, or `always`. **At most one email per run**, a summary of all changes, warnings, and errors, never one mail per entry. No flood: using `cn=status`, send one mail when a failure first appears, a reminder at most every `remind_every`, and one on recovery. `dolly check` also tests SMTP.
9. **Missing server certificate.** If an LDAPS or StartTLS connection fails because the server's CA isn't trusted locally, fetch the chain with `openssl s_client -connect host:636 -showcerts </dev/null | awk '/BEGIN CERTIFICATE/,/END CERTIFICATE/' > ca.pem` (add `-starttls ldap` for port 389). Show the fingerprint with `openssl x509 -noout -fingerprint -sha256`, and set `ca_file` in `dolly.yaml`. Code should load `ca_file` into the TLS root pool and never fall back to `InsecureSkipVerify`. See README "TLS certificates".

## Predecessor: ad2openldap

Dolly is a simplified rewrite of [ad2openldap](https://github.com/dirkpetersen/ad2openldap), which has run in production for about 15 years. The local checkout is at `../ad2openldap`. The reference implementation is `../ad2openldap/ad2openldap/ad2openldap3` (Python, ldap3). Sample config: `../ad2openldap/ad2openldap.conf`.

**Do not copy its architecture.** It exports AD to an LDIF file and diffs it against the previous export. It turns every modify into delete+add, which drops locally added group members. It falls back to a full sync that stops slapd, firewalls port 389, and deletes `/var/lib/ldap`. Dolly exists to avoid all of that.

**Do carry over its corner-case handling** (see `retrieve_ldap_userinfo`, `retrieve_ldap_groupinfo`, `flatten_groups`, `print_users`, `print_groups`):

- **Nested groups are flattened.** Members of child groups are added recursively to the parent. A cycle guard tracks the parent chain. Groups whose only members are other groups must still be emitted.
- **Resolve members by DN, not CN.** AD member DNs map to users through a `distinguishedName → objectGUID` map. CNs are not unique and often contain escaped commas (`CN=Gow\, Edward L,...`), so parse DNs properly and don't split on raw commas.
- **Required attributes:** skip, with a warning, users without `uid` or `uidNumber` and groups without `name` or `gidNumber` (the `required` lists in the mapping). Dolly relaxes this for group members, which need only a uid (see the hard requirements). Duplicate uids log a warning, and the first one wins.
- **User defaults:** a missing `unixHomeDirectory` becomes `/home/<uid>`. A missing `loginShell` gets `/bin/bash`. `gecos` is passed through. These are expressed as templates in the default mapping.
- **Empty groups:** the old tool didn't create a group until it had a member, because `groupOfNames` requires one. Dolly keeps that rule only when `member` is used (see the hard requirements).
- **Deliberately dropped:** the 65534 default for a missing `gidNumber` (such users are now ignored), the `-LS` group suffix skip, the hard-coded `ExcludedFromLDAPSync` group (use the search `filter` instead), and the `employeeID` fallback for `uidNumber`. Don't reintroduce them.
- **Group schema:** the old tree used `groupOfNames` + `posixGroup` (rfc2307bis), which is Dolly's default. RFC 2307 targets use `memberUid` only (see the hard requirements). With both attributes, write members as `member: uid=<uid>,ou=people,<base>` and `memberUid: <uid>`, sorted for stable comparison.
- **Target layout (the defaults match it):** users go under `ou=people,<base>` (RDN `uid`, `account` + `posixAccount`, `cn` = uid) and groups under `ou=group,<base>` (RDN `cn` from AD `name`). The default source for uid is AD's `uid` attribute, not `sAMAccountName` (groups-only deployments whose AD users have no `uid` map `sAMAccountName`).
- **Paging is mandatory for AD.** AD caps every search at `MaxPageSize` (1000 by default), so *every* one-level or subtree search against AD uses the Simple Paged Results control (OID `1.2.840.113556.1.4.319`, `go-ldap`'s `SearchWithPaging`) with `source.page_size` (default 500, should be ≤ `MaxPageSize`, since AD clamps larger values). Never issue an unpaged search against AD. Base-scope lookups of a single DN (out-of-scope members, and every member in a `--groups` run) are the only exception. Multi-valued attributes are capped separately (`MaxValRange`, 1500 by default), so large groups use ranged retrieval (`member;range=0-1499`, then the next range until the server returns `range=N-*`). The old code handled neither the value cap nor the ranges. Use paging for target searches too when the server supports it, but a hard server limit (such as `olcSizeLimit`) still needs `olcLimits`: a truncated result aborts the run either way.
- **Single instance:** the old tool used a pid file and broke stale locks after 20 minutes. Dolly replaces this with the LDAP run lock (see the hard requirements).
